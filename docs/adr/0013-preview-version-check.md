# ADR-0013 提交时带回预览的数据版本，系统发现已变化就拒绝

- 状态：已采纳
- 日期：2026-11-11
- 相关：ADR-0003、AGENTS 约束 2、ARCHITECTURE 3.3、INTEGRATION_RULES R3.7、ROADMAP P1-1

## 背景

两段式写入（ADR-0003）保证的是“提交的**参数**就是预览时的参数”：令牌保存预览请求，提交时回放。但确认卡片给用户看的是**变更清单**，它是系统在预览那一刻按当时的数据算出来的。从预览到用户点确认最长可以隔 10 分钟，这期间别人（或另一个对话）改了同一份数据，提交接口会按新的数据重新计算，实际落库的变更就和用户确认的清单不一样了，而平台和用户都不知道。

调度系统样例正是这样：`apply` 重新做差异计算，预览里虽然带了 `base_version`，提交时没人用它。

约束：预览和提交的参数集合必须一致（R3.2），所以版本不能作为提交接口的一个新参数；系统后端尽量少改；已接入的系统不能因为新规则而无法加载。

## 决策

用 HTTP 已有的条件请求语义，版本由系统给出、平台原样带回：

- **系统侧（R3.7）**：预览接口在返回值里加 `etag`（字符串，或整数，代表这次预览所依据的数据版本，内容由系统自定）。提交接口收到 `If-Match` 请求头且与当前版本不一致时，返回 409 或 412，不落库。
- **网关侧**：预览成功时把 `etag` 存进确认令牌（不进模型上下文）；用户确认后提交时以 `If-Match` 带回。系统答复 409 / 412 时，网关返回错误 `PREVIEW_STALE`（“预览之后数据已经变化，这次变更没有提交”，提示重新预览并重新确认），并把令牌标记为作废，之后再用同一个令牌一律得到 `PREVIEW_STALE`，不再弹确认卡片。
- **不是加载时的硬性校验**：预览不返回 `etag` 的系统照常工作，网关不发 `If-Match`，这类系统在预览到提交之间的数据变化平台发现不了。规则里写明这是系统应当提供的保护。

样例实现在 `systems/dispatch/app.py`：`etag` 为“区域 + 分组版本”。

## 考虑过的其他方案

- 网关在提交前自己再调一次预览，把变更清单和用户确认的那份比对：不需要系统配合，对所有已接入系统立即生效。没选的原因：再预览和提交之间仍有空档，给不出确定的保证；每次提交多一次可能很重的预览调用；清单里若有时间戳一类每次都变的字段会误报。它可以作为没有 `etag` 的系统的兜底，留到确有需要时再加（届时写新的 ADR）。
- 把版本作为预览 / 提交接口的请求体字段：直观，但预览时系统还没给出版本，提交的参数就比预览多一个，违反 R3.2；模型也会看到并可能改写这个值。
- 只靠系统自己做乐观锁、平台不参与：系统返回 409 时模型按现有提示会去重试，但令牌没有作废，同一份过时的预览可以反复提交；系统也拿不到“用户看到的是哪个版本”，只能和自己上一次写入比。

## 后果

- 好处：提供了 `etag` 的系统，“用户确认的清单 = 落库的变更”由系统在同一个事务里判定，没有空档；过时的预览在平台侧有明确的错误码，规则模式和模型都能如实告诉用户。
- 代价 / 限制：需要系统侧配合（多返回一个字段、多读一个请求头）；没有配合的系统没有这层保护，且平台无法在加载时发现。`If-Match` 的值是原样带回的不透明字符串，不按 HTTP 规范要求加引号。
- 后续要做的事：`python -m agent.check` 目前无法检查系统是否提供 `etag`（要真的调用预览才知道）；如果接入的写系统多起来，考虑在接入验收时加一项人工核对，或实现上面的兜底方案。
