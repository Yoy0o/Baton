# ADR-0003 写操作两段式：预览 → 用户确认 → 提交

- 状态：已采纳
- 日期：2026-10-28（2026-10-29 补记）
- 相关：AGENTS 约束 2、ARCHITECTURE 3.3、INTEGRATION_RULES 第 3 节（R3.1–R3.6）、`agent/gateway.py`

## 背景

Agent 会修改业务系统的数据（如司机换组）。模型可能误解意图、编造参数，或在用户看过预览之后又改了参数再提交。确认必须由人做，而且“用户看到的”必须就是“实际提交的”。部分调用通道（`/mcp`、`/api/ui-actions`）没有展示确认卡片的能力。

## 决策

- 清单把每个写操作拆成成对工具：预览（`risk: read`，声明 `pairs_with`）和提交（`risk: write` 或 `critical`）。没有预览接口的写操作不允许接入。
- 提交工具只接收 `confirm_token`。令牌由**网关**在预览成功后签发，绑定对话，10 分钟有效（`gateway.CONFIRM_TTL_S`），并保存预览时的完整参数；提交时网关回放这些参数，模型无法改参。
- 确认只能经运行时的 `ctx.confirm` 通道：运行时推送 `confirm_request`，等待用户决定。`ctx.confirm` 为空的调用方（`/mcp`、`/api/ui-actions`）一律拒绝写入。
- 提交请求带 `Idempotency-Key`（值为令牌），重复调用返回第一次的结果。
- 用户确认之后的提交用 `asyncio.shield` 保护：“停止”只取消等待中的部分，已确认的提交照常完成并写审计。

## 考虑过的其他方案

- 由模型在答复里请求确认、用户回复“确认”后模型再调提交：确认依赖模型自觉，且模型可以改参数。
- 单个工具带 `dry_run` 参数：预览与提交共用参数，同样无法保证提交的就是预览过的。

## 后果

- 好处：确认无法被模型绕过；提交内容与用户看到的一致；停止任务不会造成“确认了却没提交”或“没确认却提交了”。
- 代价：接入方必须提供成对接口并支持幂等键；令牌在进程内存中，服务重启后待确认的写操作作废（如实显示为中断）。
- 限制：`critical` 目前与 `write` 同样只需一次确认，二次确认和角色限制留给后续版本。
- 后续：令牌持久化（Redis 等）属于 README“v0.2 的边界”，未实现。
