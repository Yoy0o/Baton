# ADR-0011 意图识别与场景剧本：声明式剧本驱动规则模式、提示模型并参与工具路由

- 状态：已采纳
- 日期：2026-11-03
- 相关：ADR-0002、ADR-0003、ADR-0009、AGENTS 约束 1–3、ARCHITECTURE 2 / 3.1 / 3.5 / 3.7、INTEGRATION_RULES 第 11 节

## 背景

v0.2 的编排部分有三处随系统数量增长会越来越难改：

1. **意图识别写死在代码里**。`rule_planner.detect_intent` 是一串按顺序排列的正则判断，每个场景再配一个手写的 `_plan_*` 方法，里面直接写工具名、参数解析、答复文案。接入一个新系统，要让规则模式认识它，必须改 Python；判断顺序靠代码位置，没有打分和解释，也无法说明“为什么识别成这个”。
2. **识别结果只服务规则模式**。模型模式完全不用它；工具多时网关只按清单 `keywords` 做子串匹配路由，追问（“同步到调度系统”“把第 2 组列出来”）如果没提到关键词，上一步用过的系统会被过滤掉。
3. **运行时是一个大循环**。提示词组装、模型调用、工具调度、事件推送都在 `runtime._run` 里；工具调度只有“全部只读就全部并行，否则全部串行”两档；模型原样重复一个失败的调用时只能靠最大步数兜底。

约束：不能绕过网关（ADR-0002）和两段式写入（ADR-0003）；规则模式必须仍然只靠 `messages + tools` 工作，能藏在 OpenAI 兼容接口后面驱动测试（ADR-0009）；现有场景的行为和 README 验证清单的数字不能变。

## 决策

### 1. 场景剧本（playbooks.yaml）随接入清单提供

清单新增可选字段 `playbooks`，指向同目录下的 YAML。一个文件声明若干意图，每个意图包含：触发条件 `match`（`any` / `all` / `none` 词表，`re:` 前缀为正则；`slots` 要求某些槽位必须取到值）和优先级 `priority`；槽位 `slots`；前置条件 `requires`（某个工具可用 / 本对话已有某类结果 / 用户给出了某个槽位，不满足时直接答复说明）；步骤 `steps`（`call` 调工具、`show` 展示结果、`write` 预览 → 确认 → 提交）；答复模板 `answer` 与追问建议 `suggestions`。规则见 INTEGRATION_RULES 第 11 节（R11.1–R11.6），由 `agent/intents.py` 校验，违反时拒绝加载。

- 跨系统的场景放在“产出最终结果 / 被写入”的系统目录下（司机组重组放在 dispatch）。引用的系统未接入时，该意图只是不可用（不参与识别、不列为常用任务），`agent.check` 给出提醒，不阻止启动。
- 槽位提取按类型复用（`agent/slots.py`：`choice`、`flag`、`date`、`number`、`duration`、`pattern`、`assignments`）。新的参数形态用 `@extractor` 注册一个函数，剧本里按类型名引用。
- 剧本不能绕过两段式写入：`call` 步骤不得调用写操作，也不能传 `confirm_token`；写操作只能用 `write` 步骤，且 `preview` 必须在清单里声明了 `pairs_with` 指向 `apply`（R11.6）。确认仍由运行时的 `ctx.confirm` 强制，剧本只是产出与模型相同的工具调用。

### 2. 一份剧本，三种用途

- **规则模式**：`RulePlanner` 不再包含任何具体场景，只做“识别 → 按剧本推进一步”（`agent/playbook.py`）。它仍然每次从消息历史推导进度，接口不变，仍可经 OpenAI 兼容接口驱动。
- **模型模式**：运行时在每次运行开始时识别意图（只做规则匹配，不额外调用模型），把意图、已取出的参数、建议步骤、未满足的前置条件写进系统提示词的“本轮任务识别”一节，并注明“仅供参考，以用户原话为准”。识别不到时不加这一节，模型照常自由规划。
- **工具路由**：`Gateway.select` 增加 `prefer` 参数，运行时传入“识别出的意图引用的系统 ∪ 上一轮用过的系统”，与关键词命中的系统取并集。

识别结果以可选字段 `intent`（`{id, title, system, score}` 或 `null`）记在 `run_started` 事件上；`GET /api/intents?text=` 返回识别结果和提示文本，供接入方调试触发词；`GET /api/config` 的 `presets` 列出可单独发起的意图，工作台的常用任务改为来自它。

识别算法：先排除命中 `none` 的，再要求 `all` 全中、`any` 至少中一个、`match.slots` 都取到值；按（优先级，命中项数）从高到低排序，同分按声明顺序。优先级起主导作用，接入方可以明确控制“含同步字样的重组请求算重组，不算同步”这类重叠。

### 3. 运行时拆分与执行优化

- `prompt.py`：系统提示词组装（原 `runtime.SYSTEM_PROMPT`），新增意图一节。
- `executor.py`：工具执行器。按模型给出的顺序，把相邻的只读 / 只改界面调用合成一批并行执行，写操作、未知工具、参数有误的调用各自单独执行，结果顺序与调用顺序一致。无参工具的 `arguments: "null"` 按空对象处理。
- `transcript.py`：消息历史的解析（本轮调用、最近结果、上一轮用过的系统），规则模式、识别和路由共用。
- 网关新增“重复失败”策略：同一次运行里，工具名和参数都相同、且上次以不可重试的错误失败的调用，直接返回 `REPEATED_CALL` 错误信封（照常写审计），不再调用系统；界面未打开（`UI_NOT_CONNECTED`）不记为失败，因为用户可能在运行中打开页面。状态放在每次运行新建的 `CallContext.failures` 里，`/mcp`、`/api/ui-actions` 每个请求一个上下文，不受影响。

## 考虑过的其他方案

- **用模型做意图分类**（每轮先调一次模型分类）：多一次调用的延迟和费用；规则模式没有模型可用；分类结果不稳定，难以测试。规则匹配作为“参考提示”已能覆盖主要收益，模型本身仍可自由决定。
- **向量检索选工具**（设计文档 4.8 提到）：需要引入嵌入模型和索引，当前工具数（16 个）远未到需要的规模；`prefer` 路由先解决追问丢工具的问题，以后工具数上来再评估。
- **剧本放在平台级目录（如 `playbooks/`）**：跨系统场景更“中立”，但接入一个系统就要改两个地方；放在系统目录下与 `SKILL.md`、`adapter_hooks.py` 的组织一致。
- **剧本写成 Python（每个场景一个类）**：表达力强，但接入方要写代码、无法在加载时静态校验“不绕过两段式写入”，也无法自动生成帮助文本和常用任务。
- **重复失败在运行时拦截**：运行时拦截的调用不经网关，就不会写审计；放在网关里，策略和审计在同一处（ADR-0002）。

## 后果

- 好处：新系统、新场景多数情况下只写 YAML；规则模式、模型提示、常用任务、帮助文本、路由都从同一份剧本得到；识别过程可解释（命中项、分数）、可调试（`/api/intents`）；剧本在加载时就检查工具名、两段式写入、模板引用；执行器在保证写操作顺序的前提下多并行一些查询；模型空转重试会被及时打断。
- 代价 / 限制：剧本 DSL 是新的接入概念，INTEGRATION_RULES 多了一节；规则匹配仍只认识声明过的说法，对模型模式只是提示；模板语法刻意保持简单（`{名字.路径|备选|字面量}`，`when` 只支持取真 / `not`），复杂分支仍需要模型；`REPEATED_CALL` 是新的错误码，MCP 客户端和模型会看到它。
- 行为变化：轨迹回放没给司机 ID 时，原来默认回放 D0012，现在先问清楚是哪位司机（剧本 `requires.slot`）；规则模式的帮助文本改为按剧本自动生成，列出全部 6 个场景。
- 后续要做的事：工具数超过阈值较多时，评估向量检索与 `prefer` 路由的组合；考虑把识别命中情况写入审计，用于统计“哪些说法没被识别”。
