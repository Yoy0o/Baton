### P1-1 预览版本校验（ADR-0013，R3.7）

- 问题：令牌只保证提交的参数等于预览的参数；变更清单是系统按预览那一刻的数据算的，提交时调度系统样例会按新数据重新计算，预览里的 `base_version` 没人用。
- `agent/gateway.py`：`PendingConfirm.etag`（取自预览返回值，不进模型上下文）；`_commit` 以 `If-Match` 带回，系统答复 `HTTP_409` / `HTTP_412` 时令牌状态改为 `stale`、返回 `PREVIEW_STALE`；作废的令牌再次使用直接返回 `PREVIEW_STALE`，不再请求确认。审计里这类记录 `confirmed` 为真、`ok` 为假。
- `agent/providers/openapi_provider.py`：`call(..., if_match=)`；412 的修正提示与 409 相同。
- `systems/dispatch/app.py`：预览返回 `etag`（区域 + 分组版本），提交校验 `If-Match`，不一致返回 409。`systems/dispatch/SKILL.md` 补一条遇到 `PREVIEW_STALE` 的做法。
- 文档：ADR-0013 与索引；INTEGRATION_RULES R3.7、R2.9、第 9 节；ARCHITECTURE 第 1、2 节和 3.3；CHANGELOG。
- 测试：`tests/test_gateway.py::test_stale_preview_is_not_committed`（两份基于同一版本的预览，先提交一份，另一份确认后被拒、未落库、令牌作废、重新预览后可提交）。
- 没有做：网关提交前再预览一次做比对（对没有 `etag` 的系统的兜底），理由见 ADR-0013“考虑过的其他方案”。

### P1-2 模型调用健壮性

- `agent/llm.py`：限流（408 / 409 / 425 / 429）、服务端错误（5xx、529）、连接失败抛内部的 `_Retryable`，由 `_retrying` 按 `LLM_MAX_RETRIES` 退避重发（0.5、1、2…秒，上限 8 秒；有 `Retry-After` 时取较大者，上限 20 秒），用尽后报 `LLMError` 并注明重试次数。流式输出一旦推出过文字或思考过程就不再重发，报“模型输出中断”。接口返回的 `usage` 规整后随答复带回；流式请求加 `stream_options.include_usage`，接口以 400 类错误拒绝该参数时去掉重发并在本进程内记住（不会因此退回非流式）。
- `agent/runtime.py`：各轮用量累计进 `run_finished.usage`（没有用量时不带该字段）；`_trimmed` 增加 token 预算。`agent/transcript.py`：`estimate_tokens`（中日韩文字每字 1、其余每 4 个字符 1、每条消息加 4），不引入分词器依赖。

- 工作台：`store.ts` 的 `Run.usage`，`RunMessage.tsx` 在用时旁显示 token 数（悬停看输入 / 输出 / 调用次数）；重建 `web/dist`。

### P1-3 模型对照评测

- 新增 `agent/evaluate.py`（`python -m agent.evaluate`）。思路：规则模式按剧本执行，它的工具序列就是场景的参考答案，不必另外维护用例；接入新系统并写了剧本后自动被覆盖。做法：建两个互不共享数据目录的 `Platform`（一个去掉模型配置即规则模式，一个用配置的模型），对每个可单独发起的场景各跑一遍，从事件里取工具序列、是否请求确认、失败的调用、轮数、用时、用量。
- 判定：通过 = 运行完成 + 参考里的工具都调到了 + 是否走到确认与参考一致。顺序不同、多出的调用、失败后自我修正的调用、多用的轮数只作提醒。参考运行自己失败时该场景判为环境问题。
- 确认默认自动取消（验证流程走到确认，又不修改业务系统）；`--approve` 才会提交。没配模型或系统没启动时退出码 2 并说明原因。
- 测试：`tests/test_evaluate.py`（藏在假 OpenAI 兼容接口后面的规则规划器应全部一致；不肯调用提交工具的模型判不通过；`--approve` 真的提交；环境错误；判定规则）。假的 OpenAI 兼容接口从 `tests/test_scenarios.py` 挪到 `tests/helpers.py` 共用。
- 文档：README（其他检查、换模型先评测、目录）；AGENTS（命令、架构图、换模型接口一行）；ARCHITECTURE 第 7 节；CHANGELOG。
- 限制：只覆盖可单独发起的场景，追问类（`adjust`、`sync`）不覆盖；没有内嵌页面，展示步骤两边都走画布，只靠界面工具的场景（`track`、`locate`）参考运行不调用任何工具，报告里标为“未评测”、不计入通过数（端到端试跑时发现它们原先会以“0 次对 0 次”被判为通过，已改）。

## 遗留问题

1. **真实模型评测还没跑**（ROADMAP P1-3 的后半）。在有密钥的环境里启动系统后运行 `python -m agent.evaluate --json report.json`，把通过情况、多出的调用、轮数和用量补记到开发日志；若有场景不通过，先看是提示词、工具描述还是模型能力的问题。
2. 预览版本校验依赖系统返回 `etag`（R3.7）。没有返回的系统没有保护，`agent.check` 也查不出来（要真的调预览才知道）。接入新的写系统时需要人工核对；兜底方案（网关提交前再预览一次比对）见 ADR-0013。
3. 用允许列表之外的地址打开工作台时，界面只显示“断线”，原因在服务端日志里。可以让工作台在连续握手失败时提示“检查 `AGENT_PUBLIC_URL`”，但浏览器拿不到握手失败的原因，只能猜；先记在这里。
4. 评测不覆盖只靠界面工具的场景和追问类场景（ROADMAP P2-5）。
5. 发给模型的历史按估算的 token 裁剪（中日韩每字 1、其余每 4 字符 1），不是模型分词器的真实值；对中文偏保守。模型上下文很小或很大时调 `AGENT_HISTORY_TOKENS`。
6. `data/intents.jsonl` 保存用户提问的前 500 字，和对话文件一样属于运行数据（已被 git 忽略）；多用户部署时要和审计一起考虑留存与访问控制（P2-1、P2-3）。
7. 合并到 main 后打 `v0.3.0` 标签。
